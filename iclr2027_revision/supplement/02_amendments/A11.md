## 1. Scientific question

> Is perturbation sampling depth linearly recoverable from the frozen Geneformer
> representation `z`, within VCC train/validation?

Operationally: fit a Ridge probe `z -> log1p(n_cells)` on VCC train and report its VCC
validation R².

This is a **recoverability** question about `z` alone. It is **not** a specificity question
("is depth information *particular* to `z` rather than to expression generally?"), which would
require comparator arms and is deliberately not asked here (§7).

## 3. Target definition

```
t_i = log1p(n_cells_i) = numpy.log1p(n_perturbed_cells_i)      natural log, float64
```

- `n_cells_i` is a raw integer count, used untransformed apart from the `log1p` above.
- Support on the modelled rows is **[10, 121]** (`audits/geneformer_bridge_and_cell_convention.md:26`),
  so `t_i ∈ [log1p(10), log1p(121)] = [2.3979…, 4.8040…]`: strictly positive, all finite,

- The count is **truncated below at 10 by construction** — `min_cells_per_group = 10`
  (`src/data/vcc/loader.py:385`; `cache/vcc/variants/delta_hvg/meta.json`; A8). D-MECH therefore

  constructs. This is a property of the frozen row set, not a D-MECH choice, and must be stated
  whenever a D-MECH number is reported.
- `log1p` is not a new convention: the manuscript's existing count-adjusted sampling-depth
  analysis already conditions on `log(1 + n_cells)`
  (`w1_assets/tables/table_cellcount_confound.tex`; `FINAL_sampling_depth_figure_value_audit.md:67`).

**`DMECH_TARGET_USES_Y = NO.`** The target is constructed from a cell count alone. No outcome

## 7. Probe input arm

```
DMECH_INPUT_ARMS = [ z ]        — z only. One arm. One target. One cell.
```

`z` is the frozen Geneformer CLS mean-embedding delta, `mean(E_pert) − mean(E_NT)`, 768-D, raw
and never unit-normalised, taken from the committed bridge (§13). Identical to the H-FM4 `z` arm
input path.

**Comparator decision gate (lock §29 / A11 §7), answered before any result exists:**

| Q | answer |
|---|---|
| Q1 — is `z`-only sufficient for the §1 question? | **Yes.** "Recoverable from `z`" is answered by one probe on `z`. A comparator answers a different question. |
| Q2 — would C2 change the question? | **Yes, materially** — C2 (`x → 768` random projection) would test **specificity**, not recoverability. That is a different scientific claim and is not asked here. |
| Q3 — would C3 add a useful negative control? | **Marginal, and not needed.** The estimand is a **held-out** R² on genes disjoint from training; over-fitting drives held-out R² down, not up, so a positive validation R² is already self-limiting. C3 would guard a failure mode the design does not have. |
| Q4 — would matched `x` help? | **No** — a ceiling arm converts the diagnostic into a representation-versus-expression comparison, materially increasing interpretation load for a supporting diagnostic. |
| Q5 — does any frozen authority *require* comparators for D-MECH? | **No.** No authority specifies D-MECH's design at all beyond A10 §4 (§2). |

Decision: **`z` only.** Rationale: (a) it is the minimum design that answers the stated
question; (b) `lock:333` — "No control may be introduced after primary results" — makes adding
arms to a new post-unblinding diagnostic the more discretionary choice, not the safer one;
(c) a single cell removes any selection surface across arms.

**A specificity comparison is not prohibited in principle — it is simply not authorized by this
amendment.** Adding one later requires a separate amendment, fixed before that comparison is
run, and its result may not be reported as part of D-MECH.

## 10. Alpha selection and primary estimand

```
DMECH_ALPHA_SELECTION_SPLIT   = VCC validation
DMECH_ALPHA_SELECTION_METRIC  = validation R²
DMECH_PRIMARY_ESTIMAND        = validation R² of Ridge(z -> log1p(n_cells)) at the
                                validation-selected alpha
DMECH_SECONDARY_ESTIMANDS     = NONE
```

R² is `pipeline/phase1_harness.py::r2_pooled`, used verbatim, unmodified:

```python
sst = ((y - y.mean())**2).sum()
return nan if sst == 0 else 1.0 - ((y - yh)**2).sum() / sst
```

i.e. the pooled R² with the evaluation-split mean as denominator — the manuscript convention,
and the same function H-FM4 used.

Model: `sklearn.linear_model.Ridge`, single-output, `fit_intercept=True`, default solver, fit on
VCC train in float64; one probe; one target; **one cell**.

R² is chosen because alpha selection and linear-probe performance are naturally expressed in R²,
and because it matches the existing probe machinery. Pearson and Spearman correlations are
**not** computed, not reported, and may not be substituted or added after the result is seen.
No metric may be selected, swapped or supplemented after any D-MECH number exists.

### 10.1. R² estimand authority, implementation provenance, and the target mean

**Authority.** A11 §10 states the R² formula in full **and** pins the implementation the runner
must call verbatim. The formula alone fully determines the estimand given `y` and `ŷ`:

```
R2_ESTIMAND_AUTHORITY = A11_EXPLICIT_FORMULA
                        (with pipeline/phase1_harness.py::r2_pooled pinned as the
                         implementation the runner is required to call verbatim)
```

**Denominator and pooling convention — stated explicitly so the historical function name cannot
mislead.**

```
DMECH_R2_DENOMINATOR_CONVENTION = VALIDATION_SET_OWN_MEAN
DMECH_R2_POOLING_UNITS          = VALIDATION_ROWS_ONLY
```

    R² = 1 − SSE / SST
      SSE = Σ (y_val − ŷ_val)²
      SST = Σ (y_val − mean(y_val))²

The mean in the denominator is the **validation set's own mean**. The historical function name
`r2_pooled` must **not** be read as TRAIN+VALIDATION pooling, cross-split pooling, or
combined-data evaluation: D-MECH has exactly **one** evaluation split, so "pooled" is degenerate
here — it pools the 2,052 validation rows into a single R², nothing more. The historical function
is not renamed or modified (§10 pins it verbatim); only its reading is made explicit.

**Two different commits — do not conflate them.**

```
CURRENT_DMECH_GOVERNANCE_HEAD = the repository commit carrying the complete current governance
R2_AUTHORITY_LOCK_COMMIT      = the EARLIEST commit at which the currently binding R² clause
```

that introduced the current whole-file A11 SHA". A11's whole-file hash has changed at every
hardening pass while the binding R² clause has not moved; only the clause governs the estimand.

## 11. Target transform and standardisation

```
DMECH_TARGET_TRANSFORM       = log1p(n_cells)   — natural log, numpy.log1p, float64
DMECH_TARGET_STANDARDIZATION = NONE
```

Rationale. For Ridge with an unpenalised intercept, an affine change of target `y -> c·y + d`
maps the minimiser to `w -> c·w`, `b -> c·b + d` at the **same** alpha, and leaves R² unchanged.
Target standardisation would therefore alter no reported quantity while adding a fitted object,
a statistics scope to police and a further hash to pin. The minimum-preprocessing choice is
taken.

Should any future amendment introduce a target scaler, it must be fit on **VCC train only** —
never validation, never pooled. No such scaler is authorized here.

### 18.1. Technical versus biological interpretation — both remain open

**Fixed before any D-MECH result exists.** A positive validation R² is compatible with at least
two broad interpretations, and D-MECH **cannot distinguish between them**:

> **(a) Assay-level.** `z` carries information associated with sampling depth / cell yield as an
> assay property — how many cells happened to be captured for that construct-batch.
>
> **(b) Biological.** `z` carries biological information associated with processes such as
> viability, growth, perturbation severity or essentiality, which themselves affect the number of
> surviving or observed perturbed cells.

The premise is **already on the Project-B record and is not introduced here**:

- `phase4_prep.md:451-452` — "partialling an observed covariate is not causal, and `n_cells` **may
  itself be downstream of biology** (viability, A3 §3)";
- `lock_amendment_A3.md:31-33` — "**True biological effect, viability, and cell recovery may
  co-vary with `n`:** a construct whose knockdown kills cells yields fewer cells *and* may have a
  larger true effect, producing the same negative association with no statistical inflation at
  all";
- `lock_amendment_A3.md:161-162` — the motivating hypothesis, labelled as such: "Knocking down an
  essential gene may reduce viability → fewer cells recovered → *and* that gene has a larger true
  effect."

Because `n_perturbed_cells` may itself be downstream of biology, a probe that recovers it from `z`
cannot say **which** of (a) or (b) produced the recoverable signal. D-MECH measures recoverability
of the **count**; it does not decompose the count into assay and biological components, and no
such decomposition may be inferred from it.

**Required terminology.** Report the finding as

> "**sampling-depth-associated information**" or "**cell-yield-associated information**",
> "**linearly recoverable from `z` on VCC train/validation**"

and, where the ambiguity is material to the reader's conclusion, state both (a) and (b) in the
same passage. Bare "sampling depth" as the name of the recovered quantity is acceptable only
where the surrounding text has already made the (a)/(b) ambiguity explicit.

D-MECH **alone** never licenses "technical confound", "technical artifact encoded by `z`",
"Geneformer relies on sampling depth", "sampling depth causes the representation", or equivalent
mechanistic language. Separating these possibilities is a different study — A3 §3 says so of its
own VCC mechanism check — and is not attempted, authorized or resolved here.

**Honest-anticipation clause.** A positive D-MECH result would be **partly anticipated** by an
already-persisted descriptive finding: `matched_sensitivity_and_vcc_diagnostic.md` Part B
(`Z_PROPERTIES_MATCHED`) records that median `‖z‖₂` inflates at low cell count and that the
K562↔VCC ordering swaps under cell-count matching — "The embedding representation is **not**
immune to the cell-count effect." D-MECH would quantify, with a held-out linear probe, something
whose direction is already on record. It must therefore be reported as a **quantification of a
known descriptive dependence**, not as a new discovery, and its novelty must not be overstated.

**The two must nevertheless be kept distinct, in both directions.** The prior record is a
**descriptive indication** — median-`‖z‖₂` summaries compared across screens at matched cell
counts, with no probe, no held-out split and no fitted estimate. D-MECH is a **prospectively
locked quantitative diagnostic** — one Ridge probe, fit on train, evaluated on held-out
validation genes, under a frozen grid and a frozen selection rule. So D-MECH is neither a
restatement of the prior indication nor an independent discovery of it: it is a different and
stronger form of evidence about a dependence that was already visible descriptively. Do not
overstate the novelty, and do not understate the design by calling the result "already known".

## 19. Relation to the existing sampling-depth association

The manuscript already reports a descriptive association between sampling depth and the VCC
outcome:

```
Spearman rho(n_cells, y) = +0.7045   (displayed +0.705)
  VCC train+val, n = 7,792
  source: phase4/phase4_confound_diagnostic.json  VCC_reference.corr_ncells_y
  also   matched_sensitivity_and_vcc_diagnostic.md Part C
```

**This value is not recomputed by D-MECH and is not recomputed by this amendment.** It is quoted
here only to fix the boundary between the two.

| | direction | quantity |
|---|---|---|
| existing result | `n_cells` ↔ outcome | rank association between sampling depth and response magnitude |
| D-MECH | `z` → `log1p(n_cells)` | linear recoverability of sampling depth from the representation |

They are **two separate descriptive relationships involving different variable pairs**.

**Composition into a causal path is prohibited, fixed before any D-MECH result exists.** The
conjunction of the two does **not** establish, and may not be written as establishing:

- `z -> n_cells -> y`, or any equivalent chain in any direction;
- **mediation** of any kind — that sampling depth mediates, transmits or carries `z`'s
  relationship to the outcome;
- that `z`'s predictions are "**depth-driven**";
- that sampling depth **accounts for** `z`'s predictive behaviour;
- that sampling depth **accounts for** external transfer failure;
- that controlling, matching or partialling sampling depth **would remove** the observed effect.

**The one permitted joint statement.** A passage may say the two observations are "**consistent
with**" a broader sampling-depth-entanglement hypothesis **only if that same passage makes the
non-causal limitation explicit** — that these are two associations, that neither identifies a
mechanism, and that the (a)/(b) ambiguity of §18.1 is unresolved. The permission and the
limitation travel together; a "consistent with" sentence without its limitation is a violation of
this amendment, not a stylistic lapse.

**Never use "therefore"** — or "hence", "so", "which means", "implying", or any other inferential
connective — to turn the two associations into a mechanistic chain. Reported together they may
support only a **descriptive** statement that sampling depth is associated with both the outcome
and the representation.

**The prohibition is symmetric — it binds the null branch identically.**

```
DMECH_NEGATIVE_DIRECTION_COMPOSITION_PROHIBITED = YES
```

A null or non-positive D-MECH result may **not** be composed with the stored
`rho(n_cells, y) = +0.7045` to claim the **absence** of a path, mechanism, entanglement or
relationship. The two remain separate descriptive relationships on different variable pairs, and
their conjunction establishes **neither the presence nor the absence** of a causal path. A null
D-MECH result is not an argument against the stored `rho(n_cells, y)` association, which is not
recomputed by D-MECH and is not revised by it (§18, branch NULL_OR_NONPOSITIVE).

## 21. Synthetic fail-closed guards — required before any real fit

The runner must execute all eighteen synthetically and record each result. **Any failure blocks
execution.** All must run before any scientific input is opened.

| # | guard | expected |
|---|---|---|
| 1 | branch / HEAD verification | handled outside the runner, recorded in the freeze |
| 2 | thread-policy failure | `PhaseBError`: thread variable not 1 before interpreter start |
| 3 | wrong `z`-scaler hash | `PhaseBError`: scaler artifact SHA-256 mismatch |
| 4 | **Guard A** — `StandardScaler.fit` attempt through the pipeline | `PhaseBError` from the patched `fit`; counter increments |
| 5 | **Guard A** — `StandardScaler.fit_transform` attempt through the pipeline | `PhaseBError` from the patched `fit_transform` |
| 6 | `split = "test"` request | `PhaseBError` **before** any test file is opened |
| 7 | external split request (`"RPE1"`) | `PhaseBError` **before** any external file is opened |
| 8 | forbidden outcome-column request | `PhaseBError` naming the column, before the read |
| 9 | duplicate keys | `PhaseBError`: duplicate keys |
| 10 | missing keys | `PhaseBError`: keys missing between shard set and target set |
| 11 | non-finite target value | `PhaseBError`: non-finite target — never silently dropped |
| 12 | exact alpha tie | largest tied alpha selected; `tie_applied = true`; `tied_alphas` recorded |
| 13 | mixed finite / non-finite candidates | finite maximum selected; non-finite excluded |
| 14 | all candidates non-finite | `selected_alpha = null`, `status = PROBE_DEGENERATE` |
| 15 | output directory already exists | `FileExistsError`: no reuse, no overwrite |
| 16 | protected output root requested | `PhaseBError`: refuses to write under a protected root |
| 17 | **Guard B** — direct synthetic `StandardScaler.fit` on a throwaway array | the instrumented counter increments by ≥ 1 (the patched method also raises; the *counter* is what is asserted) |
| 18 | **Guard B** — direct synthetic `StandardScaler.fit_transform` on a throwaway array | the instrumented counter increments by ≥ 1 |

**Guard A and Guard B are different guards and neither substitutes for the other.**

- **Guard A (4, 5) — contract enforcement.** Drive the prohibited refit pathway through the
  pipeline and require a hard failure. It demonstrates that the pipeline *refuses* forbidden scaler refitting.
- **Guard B (17, 18) — instrumentation verification.** Invoke the instrumented
  `StandardScaler.fit` and `StandardScaler.fit_transform` **directly**, on tiny throwaway
  synthetic arrays, and require the counters to increment. It demonstrates that the patched sklearn
  methods are actually installed and reached.

Guard A passing does **not** establish Guard B: a loader-level prohibition (`refit_forbidden`) can
raise *before* `StandardScaler.fit` is ever entered, so the pipeline can correctly refuse while
the instrumentation is dead, bypassed or mis-installed. That is precisely the failure mode a
real-run count of `0` cannot distinguish from success (§21.1d).

Guard B uses **throwaway synthetic arrays only** — never `z`, never the target, never any
TRAIN/VALIDATION scientific array. Synthetic instrumentation verification is **not** scientific
fitting.

Guards 4, 5, 17 and 18 must reset their instrumentation counters to 0 before the real run, and
the reset must be recorded. That reset happens **before** the pre-run freeze; see §21.1 for what
may not be reset after it.

### 21.1. Execution-integrity invariants

**(a) Target eligibility — no repair, ever.** The frozen contract requires
`n_perturbed_cells >= 10` on every authorized aligned TRAIN/VALIDATION row (§3, §24). If any such
row violates it:

```
RUN_STATUS = HARD_STOP_TARGET_ELIGIBILITY_VIOLATION
```

The runner must **not** filter, drop, impute, replace, clip or repair the row, and must not
proceed with a reduced set. The expected row counts stay contractual: TRAIN = 5,740,
VALIDATION = 2,052.

**(b) No combined train+validation refit.**

```
DMECH_REFIT_ON_COMBINED_TRAIN_VALIDATION = NO
```

The reported result comes from a model fit on **TRAIN only** and evaluated on **VALIDATION**.
After alpha selection the runner must **not** refit on TRAIN+VALIDATION, must **not** compute a
second validation number from any refitted model, and must **not** build a final combined-data
model. Refitting on the union is a natural implementation reflex and is **not part of the frozen
estimand**; doing it would silently change what the reported R² means. The field is persisted in
the pre-run freeze, the results, the run manifest and the integrity footer.

**(c) The Ridge fit counter must stay load-bearing.**

```
RIDGE_FIT_COUNT_EXPECTED_STRICTLY_POSITIVE     = YES
RIDGE_COUNTER_OBJECT_CONTINUITY_REQUIRED       = YES
RIDGE_COUNTER_RESET_AFTER_FREEZE               = NO
RIDGE_INSTRUMENTATION_REINSTALLED_AFTER_FREEZE = NO
```

- `RIDGE_FIT_COUNT_EXPECTED` must be **strictly positive**. If the derived expected scientific fit
  count is `0`, or cannot be uniquely derived, then
  `RUN_STATUS = HARD_STOP_INVALID_EXPECTED_RIDGE_FIT_COUNT` — a counter that expects zero fits can
  never detect an unfit run, and an assertion that cannot fail is not a guard.
- `RIDGE_FIT_COUNT_OBSERVED` must be read from the **same live counter / instrumentation object**
  that produced `REAL_DMECH_RIDGE_FIT_COUNT_BEFORE_FREEZE = 0`. The object may not be
  reinitialised, rebound or swapped between the freeze and the read.
- After the pre-run freeze there may be **no counter reset, no monkey-patch reinstall and no
  instrumentation replacement**. Any of these would break the chain of evidence that the
  pre-freeze count really was zero, which is the whole point of recording it.

All four fields are persisted in the pre-run freeze and the run manifest, together with
`RIDGE_COUNTER_OBJECT_CONTINUITY_VERIFIED` — the runner's own record that the object identity
actually held, not merely that it was required.

**(d) The StandardScaler zeros must be falsifiable.** The Phase-B contract is LOAD-ONLY, so the
real-run expectation is

```
STANDARD_SCALER_FIT_CALL_COUNT_REAL_RUN           = 0
STANDARD_SCALER_FIT_TRANSFORM_CALL_COUNT_REAL_RUN = 0
```

**A zero counter is not by itself evidence that anything was checked.** A dead, bypassed or
mis-installed patch produces exactly the same zero. The zeros are meaningful only if the
instrumentation was **positively verified first**, by Guard B (§21, guards 17–18):

```
STANDARD_SCALER_FIT_CALL_COUNT_SYNTHETIC_GUARDS           = <integer, MUST BE > 0>
STANDARD_SCALER_FIT_TRANSFORM_CALL_COUNT_SYNTHETIC_GUARDS = <integer, MUST BE > 0>
STANDARD_SCALER_INSTRUMENTATION_VERIFIED                  = YES | NO
```

The expected synthetic counts are **derived and frozen before the run**; the reference design is
exactly one direct synthetic `fit` and one direct synthetic `fit_transform` per Guard B, i.e. an
expected `1` and `1`, unless the implementation naturally requires more, in which case the derived
values are frozen in the pre-run freeze and asserted exactly.

If either synthetic count is `<= 0`:

```
STANDARD_SCALER_INSTRUMENTATION_VERIFIED = NO
RUN_STATUS = HARD_STOP_STANDARD_SCALER_INSTRUMENTATION_UNVERIFIED
```

and the run stops **before** any scientific input is opened (§25 H16).

**Counter reset and continuity.** After Guard B, the synthetic scaler counters may be reset **once,
before the freeze**, and that reset is recorded. Then the freeze is written with

```
STANDARD_SCALER_FIT_CALL_COUNT_REAL_RUN_BEFORE_FREEZE           = 0
STANDARD_SCALER_FIT_TRANSFORM_CALL_COUNT_REAL_RUN_BEFORE_FREEZE = 0
```

After the freeze:

```
STANDARD_SCALER_COUNTER_OBJECT_CONTINUITY_REQUIRED       = YES
STANDARD_SCALER_COUNTER_OBJECT_CONTINUITY_VERIFIED       = YES | NO
STANDARD_SCALER_COUNTER_RESET_AFTER_FREEZE               = NO
STANDARD_SCALER_INSTRUMENTATION_REINSTALLED_AFTER_FREEZE = NO
```

The post-science real-run counts must be read from the **same live instrumentation objects** whose
operation Guard B positively verified. A violation is §25 H17. The expected real-run zeros stand —
they simply now mean something.

## 25. Hard-stop conditions

Execution stops, fails closed and writes no result if any of the following holds:

- **H1** branch is not `iclr2027-r2`, or HEAD is not the recorded starting SHA, or the tree has
  tracked modifications at launch;
- **H2** `PHASEB_REPRODUCIBILITY_GATE` is not `PASS`;
- **H3** thread policy not set before interpreter start, or a realized pool reports > 1 thread;
- **H4** any pinned SHA-256 mismatches — governing documents, environment artifacts, `z` scaler,
  bridge, or target source;
- **H5** row counts, key uniqueness or key-set equality deviate from §24 / §5;
- **H6** any non-finite target value, or any `n_cells < 10`
  → `RUN_STATUS = HARD_STOP_TARGET_ELIGIBILITY_VIOLATION` (§21.1a); never a filter or a repair;
- **H7** any of the eighteen guards fails;
- **H8** the three deterministic re-executions are not bit-identical;
- **H9** any forbidden split, forbidden column or protected root is requested;
- **H10** either StandardScaler counter is non-zero at the end of the real run;
- **H11** the output root exists, or resolves inside a protected root;
- **H12a** `R2_CLAUSE_UNCHANGED_SINCE_AUTHORITY_LOCK = NO`
  → `DMECH_ESTIMAND_FULLY_DETERMINED = NO`,
  `RUN_STATUS = HARD_STOP_R2_CLAUSE_DRIFT_SINCE_AUTHORITY_LOCK`, stopping **before** any
  scientific input is opened (§10.1); the clause is never edited or adjudicated by the runner;
- **H12** `R2_IMPL_UNCHANGED_SINCE_LOCK = NO`
  → `DMECH_ESTIMAND_FULLY_DETERMINED = NO`,
  `RUN_STATUS = HARD_STOP_R2_IMPLEMENTATION_DRIFT_SINCE_LOCK`, stopping **before** any scientific
  input is opened (§10.1); the drift is never adjudicated by the runner;
- **H13** `RIDGE_FIT_COUNT_EXPECTED` is `0` or not uniquely derivable
  → `RUN_STATUS = HARD_STOP_INVALID_EXPECTED_RIDGE_FIT_COUNT` (§21.1c);
- **H14** the Ridge counter object was reset, rebound, replaced or re-instrumented after the
  pre-run freeze, or `RIDGE_FIT_COUNT_OBSERVED` was read from a different object than the one that
  produced the pre-freeze zero (§21.1c);
- **H15** any refit on TRAIN+VALIDATION, or any second validation number from a refitted model
  (§21.1b);
- **H16** either StandardScaler synthetic guard count is `<= 0`, i.e.
  `STANDARD_SCALER_INSTRUMENTATION_VERIFIED = NO`
  → `RUN_STATUS = HARD_STOP_STANDARD_SCALER_INSTRUMENTATION_UNVERIFIED`, stopping **before** any
  scientific input is opened (§21.1d); an unverified zero is not evidence;
- **H17** the StandardScaler counter objects were reset, rebound, replaced or re-instrumented
  after the pre-run freeze, or the real-run counts were read from different objects than the ones
  Guard B verified (§21.1d);
- **H18** `Z_GUARDED_LOADS_EXPECTED` or `TARGET_GUARDED_READS_EXPECTED` is not strictly positive
  → `RUN_STATUS = HARD_STOP_GUARD_EXPECTED_COUNT_NOT_POSITIVE` (§13); an expected count of zero

- **H19** `Z_GUARDED_LOADS_MATCH = NO` or `TARGET_GUARDED_READS_MATCH = NO`

- **H20** the canonical z manifest file's own raw-byte SHA-256 does not match

  → `RUN_STATUS = HARD_STOP_Z_MANIFEST_HASH_MISMATCH` (§13), before any target read, z load, fit,
